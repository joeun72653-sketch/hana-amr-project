# 자율주행 목표지점 진입 직전 리프트 자동제어 — 설계 변경 (2026-11-05)

## 사용자 요구 — 기존 '도착 후' 순서를 대체

- **목표지점에 완전히 도착한 후가 아니라, 목표지점에 최종 진입하기 직전에** 리프트를 자동 상승/하강한다.
- 이 과정에서 로봇은 **ARM 상태(운전 준비/제어 세션)**를 유지하도록 설계한다.
- 최종 목표지점까지의 자율주행은 리프트 동작 확인 후 재개한다.
- 웹 지도에서 최종 목표, 리프트 작업(상승/하강/목표 Pulse), 진행 상태를 한 번에 관리한다.

> ARM 상태를 유지하는 것과 바퀴가 실제로 **회전 중인 것**은 서로 다른 조건이다. 우선 안전한 기본 설계는 **ARM 유지 + 바퀴 0 RPM + 주행 출력 차단 상태에서 리프트 동작**이다. **바퀴가 움직이는 중 리프트를 동시에 구동하는 설계**는 별도 위험성 평가, 전도 안정성/적재 상태/센서 사각지대/상한 속도 검증 및 하드웨어 인터록 없이는 활성화하지 않는다.

## 목표 상태 흐름

1. `IDLE` — 웹에서 출발지(기본: AMCL 현재 위치), 최종 목적지, 리프트 작업 지정.
2. `PATH_PREVIEW` — Nav2 `ComputePathToPose`로 경로·장애물·최종 접근 구역 검증.
3. `ARMED_NAVIGATING` — 단일 모드 선택기(AUTO)가 ROS → CAN 주행 명령을 소유.
4. `APPROACH_HOLD` — **최종 목표 전에 계산된 사전 정지 지점(pre-goal staging waypoint)**까지 이동하고 정지. 거리는 고정 1m가 아니라 휠 제동거리/리프트 공간/목표 접근 각도/현재 지도 환경으로 결정한다.
5. `ARMED_LIFT_HOLD` — ARM 세션은 유지하되 CAN 최종 출력 명령을 하드 게이트로 0으로 고정. 목표 주행 command=0, 실제 양쪽 RPM=0이 허용 오차 내에서 유지되고, Stop ACK/시스템 정지 인증·최신 토픽·리프트 정지/오류/간섭 검증이 완료된 경우만 리프트 작업 승인. 다른 주행 producer가 nonzero를 발행해도 CAN에 전달되면 안 됨.
6. `LIFT_MOVING` — 기존 Orgo 리프트 서버의 TOP/BOTTOM/target Pulse를 사용하되 ARM 상태용 **별도 제어 승인 토큰/하드웨어 인터락**과 지속적인 CAN 주행 차단이 확인될 때만 동작. 진행 중 리프트 위치·상태·오류를 감시.
7. `LIFT_CONFIRMED` — 모터 STOP/목표 Pulse 오차 및 이중축 위치 동기화·리프트 정지 상태 확인.
8. `ARMED_FINAL_APPROACH` — 리프트 안전 위치/적재·장애물 조건이 충족될 때만 재승인하여 최종 `NavigateToPose` 실행.
9. `COMPLETE` — Nav2 성공 + 목표 위치/자세 확인 후 웹 완료 표시.

**중요:** `ARMED_LIFT_HOLD`은 단순히 UI에서 ARM 문자열만 표시하는 상태가 아니다. 주행 출력을 한 곳에서 독점적으로 잠그고 운전 중 리프트 제어를 배타적으로 승인해야 한다.

## 현행 코드와의 차이

GitHub 기준 `amr_lift/lift_websocket.py`의 `motor_safe()`는 현재
`phase == 'DISARMED'`, `session == False`, `verified_stopped == True`를 요구한다. 즉 **현재 코드는 ARM 유지 리프트 동작을 허용하지 않는다.**

`amr_remote_client/amr_ws_to_ros.py`는 `~/.amr_motor_interlock.json`에 모터 단계, 세션 유무, 정지 검증을 기록한다. 이 파일의 상태 문자열만 `ARMED`로 바꾸거나 검사 조건만 완화하는 방식은 위험하다.

구현 시 안전한 구조를 위해 다음 변경이 동반되어야 한다.

- `amr_autonomous` 운행 조정기: 전단계 → 사전 정지 → 리프트 → 최종 접근 작업 상태 머신. 웹 재시작 후 중복 리프트 명령 금지.
- **단일 CAN 명령 게이트/소유권**: MANUAL/AUTO/리프트 정지 홀드/비상정지 순서의 명확한 우선순위. 주행/리프트 동시 활성화 하드 차단.
- `amr_ros_wheel_rpm_can.py`: CAN 최종 출력에서 락·0명령·ACK·피드백·Watchdog까지 검증. 소프트웨어 CAN publish 차단만으로 안전을 보장하지 않는다.
- `amr_ws_to_ros.py`와 `lift_websocket.py`: 'ARM 세션 유지하지만 drive-inhibited + verified stationary'인 **신규 명시적 상태**로 상호 승인; 시효 있는 인가/상태 확인과 통신 상실 시 fail-closed.
- 실물 E-stop, 독립 동력/브레이크 홀드/안전 라이다 영역, 리프트 끝단 및 간섭 센서와 감속거리 검증.
- 1000 RPM은 자율주행의 **검증 후 상한값**일 뿐이다. 리프트 이동 중 주행은 허용하지 않으며, 사전 정지 지점 접근은 별도의 안전 감속 속도를 사용한다.

## 실패 시 동작

- Nav2 PRE-GOAL 실패/취소: 리프트 동작 시작하지 않음.
- 좌우 CAN 실제 RPM 불일치·0 정지 미확인·인증 상태 만료: 리프트 금지.
- 리프트 작업 도중 CAN 주행 승인 발생/센서 차단/리프트 통신 단절/위치 불일치: 리프트 STOP 요청, CAN 주행 차단, FAULT 래치, 사용자 점검 전 자동 재시작 금지.
- 목표 리프트 위치 확인 전: 최종 접근 불허.
- 웹 창 닫힘/네트워크 단절: 상태를 안전 측으로 유지. 웹 명령만으로 안전이 보장되면 안 되며 독립 HW E-stop을 유지.

## 검증 단계

1. Nav2 경로 미리보기 + pre-goal waypoint 생성 및 웹 표시 (모터 연결 없이).
2. ARM 상태와 주행 게이트의 분리 설계/유닛테스트 + 가짜 CAN/리프트 시뮬레이션.
3. 실제 바퀴를 바닥에서 띄운 상태에서 정지/인증/회복/오류주입 검증.
4. 리프트 단독 목표 이동 검증 + 정지 인터락 확인.
5. 실제 저속 사전 정지 → 리프트 작업 → 최종 접근 시험.
6. 위험성 평가 및 충분한 정지거리/전도 안정성을 입증한 뒤에만 자율주행 상한 1000 RPM 단계별 승인.

**현황 (2026-11-05): 위 문서는 설계 요구사항이며, ARM 상태의 자동 리프트 동작 및 실물 최종 접근은 아직 구현·검증되지 않았다.**
